Arquitectura de datos — por qué es correcto

Una sola base de datos PostgreSQL. Todas las tablas tienen empresa_id. El agente de cada empresa filtra SIEMPRE por su empresa_id extraído del JWT.

Ferretería López

Empresa B

empresa_id = 2

Empresa C

Veterinaria San Roque

empresa_id = 3

Base de datos única

PostgreSQL 17

schema: setubalai

clientes (empresa_id)

facturas (empresa_id)

productos (empresa_id)

usuarios (empresa_id)

El agente filtra

JWT → empresa_id → query WHERE empresa_id = X


Empresa A nunca ve datos de Empresa B

El modelo SaaS multi-tenant con empresa_id es CORRECTO. Un solo servidor, una sola BD, N empresas aisladas. Cada mejora de código se despliega una vez y llega a todos los clientes. El costo de infra no crece linealmente con el número de clientes.
BUG ACTUAL: hay 1 cliente en BD con empresa_id = NULL. Esto rompe el aislamiento. Hay que corregirlo y agregar constraint NOT NULL en todas las tablas de datos.

Respuesta directa a tus preguntas

¿Datos compartidos en una sola BD es correcto? → SI

El aislamiento está garantizado por empresa_id en cada query. El cliente nunca ve datos de otra empresa. Esta arquitectura permite escalar a 50 clientes en la misma VPS sin cambiar nada.

¿Cada agente crece con los datos de SU empresa? → SI

Noxem guarda memoria semántica por empresa. El historial de conversaciones, las preferencias y el contexto del negocio quedan asociados a esa empresa. El agente mejora con el uso real de cada cliente.

¿Tu idea de ofrecer agentes a empresas es correcta? → SI, y es el modelo exacto que construimos

Vos vendés "un agente para tu empresa". Internamente es el mismo motor (Hermes) conectado a los datos de esa empresa. El cliente percibe un agente que conoce su negocio. Eso es exactamente lo que tenés construido.

¿Hay algo mal? → El BUG de empresa_id = NULL

Hay un cliente en la BD sin empresa_id asignado. Si el agente lo encuentra y lo devuelve a otra empresa, hay una fuga de datos. Hay que corregirlo más agregar NOT NULL en todas las tablas de datos.
